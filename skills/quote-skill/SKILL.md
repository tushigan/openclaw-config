# 内部报价 Skill

## 适用场景

这个 skill 用来处理公司内部正式报价。它会把会议纪要、聊天记录、需求说明等资料，整理成公司统一格式的 `HTML / PDF / Excel` 报价文件，并把项目记忆留在当前 skill 目录里。

项目目录默认放在：

- `projects/客户名/项目名/`

如果当前是从业务项目切入报价，也可以直接放在：

- `/Users/a123/.openclaw/workspace-business/projects/客户名/项目名/quote/`

本 skill 已内置本地 Python 依赖目录 `python/`。如果迁机器后依赖缺失，先运行：

- `python3 scripts/bootstrap_runtime.py`

如果当前调用方是 `workspace-business` 下的 shared 业务专家，为避免 protected path 限制，优先通过本地 wrapper 调起正式脚本：

- `python3 /Users/a123/.openclaw/workspace-business/scripts/run_quote_skill.py <script_name> ...`

## 开始前先做什么

1. 先判断这是新项目还是旧项目。
2. 如果是旧项目，先读当前报价项目目录下的 `project.json`、最新版本的 `version.json` 和已有输出。
3. 如果是新项目，先用 `scripts/init_quote_project.py` 建项目目录。
4. 若本次报价来自业务项目，先读业务项目里的 `quote-handoff.json`。
5. 先尽量读完会议纪要、聊天记录、项目背景、需求说明等资料，再建议案子类型。
6. 读完资料后，再让用户确认属于 `散案 / 项目案 / 全案`。
7. 报价不自动算价格，价格仍由人来确认。

## 核心参考资料

1. 先读 `references/company-standards.md`，确认写法和版式规则。
2. 先读 `references/service-catalog.md`。
3. 正式搭结构前，读取 `data/service-catalog.json`。
4. 选输出规则时，读 `references/output-rules.md`。
5. 更新版本时，读 `references/versioning-rules.md`。

## 固定工作流

1. 先读资料，再建议案子类型。
2. 用户确认 `散案 / 项目案 / 全案` 后，再进入正式拆解。
3. 如果 `assets/standards/service-catalog.xlsx` 更新过，先重建 `data/service-catalog.json` 再继续。
4. 正式报价必须优先从公司标准服务清单里选服务项，再组合成本次结构。
5. 正式结构统一按三层组织：
   - `散案`、`项目案`：`阶段 > 项目 > 任务`
   - `全案`：对外可理解为 `服务模块 > 项目 > 任务`，但内部仍是同一套三层数据
6. 结构检查要按案子类型切换：
   - `散案`、`项目案`：如果某个阶段项目数不够，或者某个项目任务数不够，要先明确告诉用户当前 `拆分不够`，不要直接生成正式报价。
   - `全案`：允许 `服务模块 > 项目 > 任务` 保持最小展开，但不能是空壳；同时必须先确认年度目标、周期、服务边界和核心模块完整。
7. 说明按任务颗粒度写，交付物优先写在项目层，必要时再写阶段层。
8. 正式报价先完成输出，报价完成后再整理待入库清单并询问是否纳入公司标准服务清单。
9. HTML 是内部主稿，PDF 固定由 HTML 转出，Excel 与它们共用同一份正式结构数据。
10. 若当前会话来自 Feishu，且用户明确要“发文件 / 发报价 / 交付报价”，必须把“生成文件”和“发送文件”当成两个独立步骤执行完，不能只返回本地路径。
11. 先完成报价，后处理清单沉淀。
12. 不得自己另造一套预览 JSON 或手写最终 HTML 来绕过正式结构校验；只要要生成正式报价，就必须回到标准 `quote-content.json` 结构和正式脚本链路。

## 任务拆分原则

1. 先按客户真实需求、当前服务边界和公司标准服务清单判断能做哪些真实动作，再拆任务。
2. 默认目标不是“刚好过结构校验”，而是“在真实范围内尽量拆细，让用户能看见清晰的服务价值感”。
3. 只要某个动作满足以下任一条件，就优先拆成独立任务：
   - 可以单独讲清楚价值
   - 可以单独形成交付或确认节点
   - 可以单独修改或返工
   - 可以单独对应服务清单条目
4. 如果某个项目在当前客户需求下确实只能落成 2-3 个任务，可以保留，不要硬拆假任务。
5. 但 `包装策划 / 包装设计执行 / 包装落地 / 婚庆专项 / 详情页策划 / 详情页设计表现 / 主图策划设计 / 渠道策略` 这些板块默认属于高可拆板块。除非客户范围明显收窄，否则不要只写很少几项就停。
6. 对高可拆板块，正式落稿前必须先检查服务清单里是否还有适配条目可纳入；确认不适用后，才允许保留较少任务数。

## 高可拆板块的常见细拆方向

以下不是强制全选，而是默认优先检查是否适配本次客户需求：

1. 包装策划 / 包装设计 / 包装落地
   - `产品体验切片`
   - `包装触点分析`
   - `包装风格定位`
   - `包装结构造型设计`
   - `包装开启方式设计`
   - `包装画面设计`
   - `包材建议`
   - `包装创意提案`
   - `包装工艺及材质建议`
   - `包装数码打样测试`
   - `包装印前文件输出`
   - `包装印刷效果反馈及跟踪执行`
2. 渠道策略 / 婚庆专项
   - `区域策略`
   - `平台策略`
   - `渠道平衡策略`
   - `渠道定位规划`
   - `客户策略`
   - `产品名产品Slogan`
3. 详情页策划 / 详情页设计 / 主图
   - `竞争品牌详情卖点分析`
   - `详情页转化策略`
   - `卖点框架搭建`
   - `产品详情页创意`
   - `产品详情页创意草图`
   - `产品详情页摄影脚本`
   - `拍摄远程跟踪及修图`

   - `主图核心卖点策划`
   - `主图排版设计`

## 表格合并硬规则

正式报价表格的“合并单元格”不是靠手写空白 `<td>` 模拟，而是靠结构化数据驱动渲染器自动生成 `rowspan`。

必须遵守：

1. 正式交付版 `HTML / PDF / Excel` 必须从 `quote-content.json` 通过脚本渲染，不能手写最终表格 HTML。
2. 同一个阶段下，凡是应该纵向合并显示的内容，必须通过 `阶段 > 项目 > 任务` 三层结构表达，不能把同一个项目拆成多个平级 project 再靠空白单元格凑视觉效果。
3. 同一个项目下有多个任务时：
   - `project_name` 只保留一份
   - `project_deliverables` 只保留一份
   - 由渲染器自动合并为跨多行单元格
4. 同一个阶段下有多个项目时：
   - `stage_name` 只保留在阶段层
   - 由渲染器自动合并整段阶段单元格
5. 如果某一项内容本质上应该并列为多个任务，就拆成多个 `tasks[]`；如果本质上只是一个任务，不要为了“看起来能合并”硬拆假任务。
6. 禁止交付这种伪合并结构：
   - 前一行写 `项目`
   - 后几行把 `项目` 列留空
   - 但 HTML 没有 `rowspan`
   这种做法在浏览器里不会真的合并，属于无效结构。

## 飞书交付规则

1. `HTML` 用于内部归档、浏览器预览和 PDF 转出，不作为飞书聊天里的默认最终交付件。
2. 当前会话若是 Feishu 直连用户或群聊，且用户明确要文件：
   - 先运行 `scripts/render_quote_bundle.py`
   - 至少生成并发送 `PDF`
   - 若 `XLSX` 已生成，也应一并发送
3. 非图片报价文件必须通过飞书真实文件发送，优先使用 `message` 工具附件发送；不得只回复本地绝对路径、链接或 `MEDIA:/...` 文本。
4. 若当前只是回传给上游 agent，则必须明确写“文件已生成但尚未对最终用户发送”，并附绝对路径；不能把路径写成已交付。
5. 如果 `PDF` / `XLSX` 生成失败，必须明确报错并说明当前仅完成到哪一步；不得说“发你了”。

## 交付前检查

正式输出前必须做这四步：

1. 先逐项目做一次任务细拆自检：
   - 当前项目是不是只满足最低结构，没有把真实服务动作尽量拆开
   - 当前项目是不是高可拆板块，却只写了很少任务
   - 服务清单里是不是还有明显适配但尚未纳入的任务
   - 如果最后仍只有 2-3 个任务，原因是不是客户范围本来就收窄，而不是自己偷懒少写
2. 再运行 `scripts/render_quote_bundle.py` 生成正式文件。
3. 再运行 `scripts/validate_merge_semantics.py` 检查 HTML 是否真的生成了应有的 `rowspan`，确认没有“空白单元格假装合并”的伪结构。
4. 若当前会话为 Feishu 且用户要求文件，输出完成后必须把 `PDF` / `XLSX` 作为真实附件发送，再回复版本信息。

## 常用脚本

1. `scripts/build_service_catalog.py`
   - 从人工维护的主清单重建机器读取版 `data/service-catalog.json`
2. `scripts/init_quote_project.py`
   - 创建新项目目录和基础记录文件
   - 支持两种模式：
   - `--projects-root + --client-name + --project-name`
   - `--project-dir + --client-name + --project-name`
3. `scripts/create_quote_version.py`
   - 创建下一版并延续上一版内容
4. `scripts/bootstrap_runtime.py`
   - 检查并补装本 skill 运行所需的本地 Python 依赖
5. `scripts/render_quote_bundle.py`
   - 正式串起整条输出链路：
   - 先确保服务清单 JSON 是最新的
   - 再读取并校验 `quote-content.json`
   - 先输出 `quote.html`
   - 再生成 `quote.pdf`，优先走浏览器链路；不可用时自动回退到本地 Python PDF 渲染
   - 最后输出 `quote.xlsx`
   - 输出完成后，再把本次新增待入库项写入公司总待入库池
6. `scripts/validate_merge_semantics.py`
   - 检查 `quote.html` 是否真实使用了 `rowspan`
   - 检查阶段 / 项目 / 项目交付物 这些本应合并的内容有没有退化成“空白单元格伪合并”

## 输出后要落盘什么

1. 更新 `project.json`
2. 更新当前版本的 `version.json`
3. 记录本版使用过的 `service_catalog_refs`
4. 记录本版案子类型 `case_type`
5. 记录本次新增待入库项
6. 如果已经进入公司总待入库池，同时记录对应的待入库池条目 ID
